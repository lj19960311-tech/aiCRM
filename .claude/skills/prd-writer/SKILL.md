# PRD 撰写与修改

帮助产品、研发、算法、设计和测试理解本次交付范围、业务规则及可验证结果。以用户当前任务决定内容和篇幅。

## 先确定本次任务

- **新建 PRD**：读取资料，选用 [PRD 模板](reference/prd-template.md) 中相关部分；完整需求沿用四段式主线，纯埋点或单点需求可采用简版。
- **局部修改或补全**：先读目标文档及受影响内容，保持原结构、术语、规则编号和已确认决定；只修改指定内容及由此必须同步的流程、数据、交互、异常和验收引用。不要为了套模板补齐无关章节。
- **明确要求重写**：保留已确认事实与本期范围，默认另存新版本；用户明确要求原位修改时遵从该要求。
- **只分析或检查**：需求分析交由 `requirements-analysis`，逻辑检查交由 `prd-logic-audit`；不把检查请求变成写入。仅在该工作确实需要且技能可用时使用，不强制每次写作串行执行分析、审计或六角色评审。

用户明确要求优先于本 Skill 的默认写法；保存位置、备份和项目术语遵循适用的项目约定。用户已确认的范围和规则不因模板示例而改变。

## 读取依据与处理缺口

1. 支持现有 PRD、需求分析、会议纪要、Word、原型、接口资料和用户补充；采用可用工具读取，不以 `.md` 格式或独立需求分析文档作为准入条件。
2. 新建时读取所需材料；修改时读取原文及直接关联内容。确认目标、受众、范围和交付形式，已明确的信息不重复询问。
3. 记录实际使用的资料及版本。用户最新明确确认作为本次修改依据；其他资料互相冲突时列出冲突，不仅凭文件日期判断哪份有效。缺少被引用的资料时说明缺口，不声称已核验。
4. 区分已确认需求、待确认项和建议。推断不能成为正式业务规则；不编造角色、权限、阈值、排序、接口、事件、指标目标或异常能力。原型样例和演示脚本不能证明生产规则或接口已实现。
5. 缺口影响目标、本期范围或核心业务逻辑时，集中询问相关问题；先完成不依赖答案的部分。其他缺口用 `TBD` 标记并继续，存在多项时使用模板的待确认清单。用户要求先出稿时可形成草稿，未决分支不替用户作决定。
6. 区分本期交付、后续规划、已有能力和 Demo 占位。关键开发或验收口径仍未确认时标记为草稿；不得因生成结束而声明已评审通过、已上线或已测试通过。

## 按实际任务选用内容

章节编号指向模板位置，用于选材，不要求每份 PRD 保留全部章节。

| 任务类型 | 重点内容 | 选用方式 |
| --- | --- | --- |
| Agent / 对话 / 知识与报告 | 触发与必要信息、AI 输入输出及正确性、意图与上下文、Skill/Tool 边界、确认和产出物 | 按需使用 03.3、04.2、06、08、10—12；未涉及知识库或文件时省略相应内容 |
| 客户/线索评分、个性化推荐 | 评分对象、数据范围、过滤顺序、公式或模型输出、排序、时间口径、理由与依据 | 重点展开 03.2、07、08 和 15；区分规则计算、模型预测和生成式解释，不预设所有推荐都用权重加总 |
| 工作台、领养接入、应用中心、多端交互 | 本期功能、用户动作与结果、状态迁移、权限、保存生效、端间差异 | 重点展开 03、05、06—07、09、11；确定性交互无需增加 Agent 或意图路由 |
| 数据埋点及统计口径 | 统计范围与职责、指标、公共参数、事件时机、字段级统计、去重 | 使用 00—01、06—07、14，按需加验收和未决项；可按“背景与范围→职责→指标→参数与事件→字段口径”组织，不扩展业务功能、模型评估或看板 |

混合任务只组合实际涉及的内容。业务规则以当前项目确认结果为准，不把某份 PRD 的数量、期限、等级、字段或行业配置复制为通用默认值。

## 写作和同步规则

- 新建完整 PRD 默认保持背景与目标合计不超过 200 字；用户故事仅在角色、场景或权限差异需要解释时保留。已有文档不因这个默认限制被无关压缩。
- 同一业务规则只在一个位置完整定义，其他位置引用规则编号或章节；流程、提示词和验收不得另行定义一套数值或条件。
- 流程有分支、跨角色交接或状态变化且图示有助于理解时使用 Mermaid；简单顺序可用文字步骤。只画有依据的节点，保留已知必要确认顺序，不使用固定 Agent 流程套所有需求。
- 评分/推荐需求说明业务判定和已知计算口径，算法或接口细节未确认时保留 TBD。规则配置、预测分数、概率、等级和展示理由不能相互替代；生成式解释不得改写系统返回的分数和排序。
- 数据来源与字段、界面展示与用户动作、状态与异常分别在最合适位置定义；只对需求实际涉及的权限、空值、时间边界、重复操作等问题补充说明，不扩展无关状态。
- Prompt 引用业务规则，避免复制维护；不得把权限、硬规则和写入约束仅放在 Prompt 中。产品内需要什么确认由已确认业务规则决定，不擅自增加二次确认弹窗。
- 功能验收写清前置条件或输入、可观察的预期结果及规则依据。测试用例是待执行内容；有未决口径的用例标记依赖，不能写成已通过。效果指标按需填写，不以业务提升目标代替功能验收。

## 交付前检查

按本次变更范围检查，不自动扩大为全项目审计：

- 用户明确要求均有落点，未新增无依据的功能、规则、指标或技术实现；建议、Demo 和后续内容未进入本期必做范围。
- 本次涉及的规则、流程、数据、页面、异常、验收及待确认项相互一致；保留原有决定，更新关联引用，不全篇重编号。
- 涉及 PRD 与原型对齐时检查指定的配套文件；未读取或未修改的文件明确说明，不宣称自动同步。
- 涉及数值时核对公式、单位、边界和示例；涉及指标时核对统计对象、时间窗口和去重口径。仅对本次用到的内容执行。
- 检查表格列数、章节/规则引用、文件链接和图示语法；正文占位符替换为真实内容或 TBD，模板教学说明不混入交付文档。

## 保存与反馈

按用户指定形式交付；未指定时，文件任务沿用现有格式和项目目录，新建文本 PRD 可用 Markdown，聊天中要求整理的内容可直接回复。不要固定创建 `./prd`，不要默认同时生成 Word、PDF 或评审报告。

修改前按项目约定备份；没有备份约定且需要覆盖已有文件时保留可恢复副本。只有用户要求或适用项目约定已授权时才执行发布、消息发送或远程同步。

交付时简要说明实际修改、重要未决项、执行过的检查及文件位置。格式检查不能证明业务规则正确；未执行的测试、未核验的接口和线上状态不得报告为已通过。
